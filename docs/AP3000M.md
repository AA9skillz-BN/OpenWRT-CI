# AirPi AP3000M 固件（OpenWRT-CI 地基）

AP3000M 通过 `DEVICE-CORE.yml` 构建，直接执行机型钩子。
共享阶段、版本锁及发布规则见[构建流程](BUILD-PIPELINE.md)。

| 文件 | 作用 |
| :--- | :--- |
| `Config/AP3000M.txt` | 单机型配置：`mediatek/filogic` + `airpi_ap3000m`，选中 FM350 与风扇控温 |
| `.github/workflows/AP3000M.yml` | 入口工作流，调用 `DEVICE-CORE.yml`，可手动触发 |
| `Scripts/AP3000M/private.sh` | 投放 FM350 配置、OTA、RNDIS 自愈和网络调优脚本及构建标签 |
| `Profiles/AP3000M.json` | 配置片段、插件选择、必需包和最终镜像校验要求 |
| `docs/AP3000M.md` | 本说明 |

## 目标设备

| 项 | 值 |
| :--- | :--- |
| 机型 | Airpi AP3000M 5G CPE |
| 平台 | `mediatek` / `filogic`（`airpi,ap3000m`，上游已支持，无需打 DTS 补丁） |
| 主控 | MediaTek MT7981B（2×A53）+ MT7976 DBDC WiFi |
| 存储 | 8G / 16G eMMC，产物为 `sysupgrade-tar`（`...sysupgrade.bin`） |
| 内核 | 6.18（主线） |

## 集成的两个插件

统一安装阶段按 `Profiles/AP3000M.json` 选择插件，用
`Profiles/packages.lock.json` 中的完整提交 SHA 下载，不经过通用 `Packages.sh`：

| 上游仓库 | 克隆到 | 生成的包 |
| :--- | :--- | :--- |
| [`LianXia233/luci-app-fm350`](https://github.com/LianXia233/luci-app-fm350) | `package/luci-app-fm350` | `luci-app-fm350`（LuCI JS + Rust `fm350d`） |
| [`LianXia233/luci-app-airpi3000m-fancontrol`](https://github.com/LianXia233/luci-app-airpi3000m-fancontrol) | `package/luci-app-airpi3000m-fancontrol` | `luci-app-airpi-fancontrol`（温度曲线 / 无极调速）<br>`kmod-airpi-gpio-fan`（GPIO 软 PWM，`/sys/kernel/duty_cycle`） |

`Config/AP3000M.txt` 里对应四行：

```
CONFIG_PACKAGE_luci-app-fm350=y
CONFIG_PACKAGE_luci-app-airpi-fancontrol=y
CONFIG_PACKAGE_kmod-airpi-gpio-fan=y
CONFIG_PACKAGE_kmod-hwmon-pwmfan=y
```

## 怎么跑

GitHub → Actions → **AP3000M** → *Run workflow*。

| 输入 | 默认 | 说明 |
| :--- | :--- | :--- |
| `SOURCE` | `immortalwrt/immortalwrt` | 源码仓库 `owner/repo` |
| `BRANCH` | `master` | 源码分支 |
| `PACKAGE` | 空 | 临时追加插件，`\n` 分隔，等价于往 `.config` 追加 `CONFIG_PACKAGE_xxx=y` |
| `SOURCE_MODE` | `locked` | 按 `Profiles/sources.lock.json` 锁定源码和 feeds；显式选择 `latest` 才跟随上游 |
| `BUILD_ONLY` | `false` | 完整编译和校验后只上传 Artifact，不创建 Release |
| `TEST` | `false` | 开则只跑 `make defconfig` 并上传 `Config-*.txt`，不编固件（验证配置用，约 10 分钟） |

### 关于 “main”

- **ImmortalWrt 源码仓没有 `main` 分支**：主线开发分支叫 `master`，当前内核 6.18。
- **OpenWrt 上游**已把 `master` 重命名为 `main`（两者指向同一提交）。
- 因此默认组合是 `immortalwrt/immortalwrt@master`（ImmortalWrt 主线）。想直接编 OpenWrt 主线就填
  `SOURCE=openwrt/openwrt`、`BRANCH=main` 并选择 `SOURCE_MODE=latest`。其他源码组合需要重新验证。
- 注意 `VIKINGYFY/immortalwrt` 的 `main` 是**高通专用**分支（自述“无法编译其他平台”），不要用于 MTK。

## 产物

TEST 上传配置预览；BUILD_ONLY 上传经校验的固件 Artifact。两者都关闭时，
独立发布 job 才创建 Release。标签包含机型、源码、分支、时间、run ID 和 attempt，
非 main 分支额外使用 `preview-` 前缀并标为 prerelease。主要文件：

- `...mediatek-filogic-airpi_ap3000m-squashfs-sysupgrade.bin`（升级/首次刷写用）
- `Config-AP3000M-*.txt`（本次实际生效的配置，便于复现）
- manifest、SHA-256 校验和、源码/feeds/插件版本锁及镜像校验证据。

## 内置工具

| 工具 | 位置 | 说明 |
| :--- | :--- | :--- |
| **ttyd** | LuCI → 系统 → **终端** | 浏览器直接开 root shell；`ttyd` 服务默认监听 7681，随 LuCI 登录态使用。救援/改配置不用再开 SSH |
| FM350-GL | 网络 → Mobile Network → FM350-GL | 模组状态、拨号、锁频、短信、AT 透传 |
| 风扇温控 | 状态 → 风扇控制 | 自动温控/手动档位，eMMC 容量自适应硬软 PWM |
| **一键 OTA** | LuCI → 系统 → **固件升级**（图形界面）<br>命令行 `ap3000m-ota`（ttyd） | 见下节 |
| **RNDIS 自愈** | 开机自动（`ap3000m-rdnis-guard`，S98） | 检测 `rx_packets=0` 且 `tx_packets/tx_errors>0` 的端点卡死，自动 `AT+CFUN=1,1` → 重新定位 AT 口 → 重启 fm350d；也可手工 `ap3000m-rdnis-guard --check` / `--force` |
| **RNDIS 调优** | 自动（hotplug `20-ap3000m-net-tune`）+ `ap3000m-net-tune` 手工 | RPS/XPS 双核分摊、txqueuelen 2000、MTU 实测、BBR、软件 flow offload —— 见「数据面调优」一节 |

## 一键 OTA

两种入口，后端同一个 `/usr/sbin/ap3000m-ota`：

**① LuCI 图形界面：系统 → 固件升级**

| 区域 | 内容 |
| :--- | :--- |
| 版本卡片 | 当前版本（读 `/etc/ap3000m-build.tag`）/ 检查到的最新版本 / 大小 / sha256 前 12 位 / **上次检查时间** |
| 按钮 | `检查更新` → `下载并校验` → `升级（保留配置）` / `升级（不保留配置，二次确认）` |
| **回滚** | 下拉列出 `/root/ota` 中带校验记录的其它版本；回退前重新核对大小、SHA-256 和设备兼容性 |
| 进度 | 后台下载时实时显示百分比（页面每 3 秒轮询，字节数取自 `.part` 文件大小） |
| 选项 | 「默认保留配置」「下载走镜像」两个开关，写入 `/etc/config/ap3000m_ota` |
| 结果 | 上次升级成功/失败（由 S99 开机脚本回写） |
| **自动检查** | 首次开机装好 cron：每天 04:15 跑 `check --cache`，结果写 `/tmp` 缓存；页面打开即显示，不必等网络 |

> 发布前按 `Profiles/AP3000M.json` 检查单设备配置、必需包、tar 结构和设备元数据，
> 并解开实际 FIT/DTB 与 squashfs 检查设备标识、关键脚本、启动链接及本次构建标签。
> 必需包丢失或内容不符直接失败，不会先发布再事后裁剪附件。

**② 命令行（ttyd 里，无需 SSH）**

```sh
ap3000m-ota check                    # 看有没有新版本（当前 / 最新 / 大小 / sha256）
ap3000m-ota list                     # 列出可用正式版本
ap3000m-ota upgrade                  # 一键升级，**保留配置**（默认）
ap3000m-ota upgrade --wipe --yes     # 不保留配置（清空 WiFi/密码/插件配置）
ap3000m-ota upgrade --tag <TAG>      # 指定版本（可用于回退）
ap3000m-ota status                   # 当前版本 / 待验证升级 / 上次结果 / 本地镜像
ap3000m-ota self-update              # 从兼容的正式版附件更新 OTA 工具
ap3000m-ota self-update --tag <TAG>   # 指定正式版的 OTA 工具
```

工作机制：

| 环节 | 实现 |
| :--- | :--- |
| 当前版本 | 构建期写入 `/etc/ap3000m-build.tag`，值就是 Release tag（`AP3000M-<源>-<分支>-<时间>-<run ID>-<attempt>`） |
| 版本来源 | `api.github.com` 的 releases（取 `tag / size / digest(sha256)`）；排除草稿和预发布，默认渠道为 `AP3000M-immortalwrt-master-` |
| 下载镜像 | 先走 `ap3000m_ota` 配置里的 `list mirror`（默认 `gh-proxy.com`、`ghfast.top`），全失败回落 GitHub 直连 |
| 完整性 | 强制 `sha256` 校验（来自 GitHub API，不信任镜像站）；失败即删、不刷 |
| 配置保留 | 默认 `sysupgrade`（保留 `/etc/config`）；`--wipe` 才 `sysupgrade -n` |
| 升级结果 | 完整性与 `sysupgrade -T` 检查通过后才写 `/etc/ap3000m-pending`，开机由 S99 服务调用 `boot-hook` 回写结果 |
| 断点信息 | 下载落盘 `/root/ota/`（eMMC，不占内存）；升级前自动 `sysupgrade -b` 备份配置 |

配置项：`/etc/config/ap3000m_ota`（`repo` / `tag_prefix` / `keep_config` / `use_mirror` / `dir` / `mirror` 列表）。

`self-update` 只接受当前机型渠道的正式版附件，不再读取 `main` 或其他分支。
附件为 `ap3000m-ota` 和 `ap3000m-ota-update.json`，均纳入 `sha256sums`。
设备先核对 GitHub API 提供的大小和 SHA-256，再核对更新元数据中的
`runtime_abi`、标签、脚本摘要及依赖命令，最后做 shell 语法检查。
通过后在同一文件系统原子替换脚本，保留 `/usr/sbin/ap3000m-ota.bak`，
并与下载/刷写共用 flock。不会执行下载来的代码来检查兼容性。

兼容标记随固件安装在 `/usr/share/ap3000m-ota/runtime-abi`，自更新不会改它。
旧固件缺少标记、正式版没有更新附件或兼容版本不符时，需先整包升级。
已有旧脚本不会被远程自动修正；这项限制需要安装新版固件后生效。
兼容版本是维护者声明，不等于真机验证；今后改变 UCI/RPC/UI 契约或新增不兼容依赖时，
必须递增 `Scripts/AP3000M/ota/runtime-abi`，不能只依赖哈希和语法检查。

> 注意：
> 1. **本次之前刷入的旧固件没有 `/etc/ap3000m-build.tag`**，`check` 会显示 `unknown-r0-…`，升级一次后即正常。
> 2. 镜像前缀是第三方公益服务，**必须依赖 sha256 校验**（脚本已强制）；若某天全挂，`use_mirror=0` 可强制直连。
> 3. 平台没有 A/B 分区，升级期间**不要断电**；想稳妥就先 `ap3000m-ota download` 只下载，再择机 `upgrade`。
> 4. 构建校验不等于真机 OTA 验证；实际升级应先备份配置，并核对机型和目标版本。

## 数据面调优（把 RNDIS 榨干）

FM350 只有 RNDIS 一种数据通路（`AT+GTUSBMODE` 仅 40/41，两个组合都是 RNDIS），没有 ECM/NCM 可选。
所以固件改成「把这一条通道的参数调到最优」，由 `Scripts/AP3000M/net-tune/` 在构建期投放：

| 手段 | 实现 | 生效时机 |
| :--- | :--- | :--- |
| **RPS/XPS 双核分摊** | `rps_cpus` / `xps_cpus` 写 CPU 掩码（2 核 = `3`） | hotplug：接口一出现就写（USB 自愈重建后也会重写） |
| **txqueuelen** | 2000 | 同上 |
| **MTU 实测** | `ping -M do -s` 从 1500 递减实测，结果缓存 `/etc/ap3000m-mtu` 并写 `network.fm350.mtu` | 接口拿到 IPv4 后 10 秒 |
| **BBR** | `/etc/sysctl.d/99-ap3000m-tune.conf`（含 8MB 缓冲、`tcp_mtu_probing=1`、`fastopen=3`） | 开机 sysctl |
| **软件 flow offload** | `firewall.@defaults[0].flow_offloading=1`（`kmod-nf-flow` 镜像已有） | 首次开机 uci-defaults |

手工查看/调：

```sh
ap3000m-net-tune status     # 当前 MTU / tx_queue_len / rps_cpus / 拥塞控制
ap3000m-net-tune apply      # 立即重新应用
ap3000m-net-tune probe      # 重新实测 MTU
```

> 硬件 offload（`flow_offloading_hw`）刻意不开：上游是 USB RNDIS，MTK 的 PPE 在以太网 MAC/交换侧，
> 5G 这条链吃不到；开了也没收益。真想要 HNAT 得换 chasey 的 6.12 树整套重做。

## FM350 USB 2.0 兼容选项

2026-10-29 真机排查中，FM350（0e8d:7127、81600.0000.00.29.23.17）在
USB 3.0 下复现接收为零、发送错误和队列超时；USB 2.0 下完整重启模组并重新拨号后，
路由器公网探测、电脑经 AP Wi-Fi 的 DNS/HTTP/HTTPS 及用户手机上网均恢复。
一次整机软件重启后仍通过，试验期间接收约 390 MB、发送约 37 MB，USB 收发错误为零。
这些结果支持此设备的兼容方案，尚不能区分模组固件、内核、信号完整性或供电根因，
也不能证明所有 FM350 都需要降速，或长期稳定性已验证。

后续固件内置 `/etc/init.d/ap3000m-fm350-usb-compat`，默认不改变 USB。
明确需要该方案时，设置 `fm350.main.usb2_compat=1`、提交 UCI 后重启；S90 服务在
fm350d 的 S95 之前禁用已核对拓扑的 USB 3.0 端口，使模组走 USB 2.0。
服务限定 AP3000M 的已核对端口；若端口已有设备，只接受已知 FM350 产品号。
遇到不同设备、不同拓扑或正在运行的拨号守护则拒绝切换。
设回 `0` 并重启即可恢复通常的 USB 3.0 连接选择。兼容模式会限制峰值吞吐。
本次板端热修复也保留了独立回退脚本；已发布固件附件未被替换。

本次同时观察到插件把 CGCONTRDP 的 IPv6 DNS 计入会话地址、进而误判 PDP 激活的独立问题。
机型钩子对锁定源码应用精确校验补丁：DNS 只进入 DNS 列表，地址只取目标 CID 的地址字段，
保留 CGACT 明确状态的优先级和有效 IPv6 会话。Linux 回归通过真实插件的串口/PDP/拨号
入口重放空地址、残留地址、IPv6 DNS、其他 CID 和激活状态响应；此解析修复仍不能
证明 USB 3.0 发送队列超时的根因，也不改变上述兼容选项。镜像闸门要求安装的 fm350d
与本轮编译产物逐字节一致；新二进制仍需要完整构建和真机验收。

## 风扇页面调速修复

2026-10-29 在本机复现：自动温控正常，但点击手动档位或应用滑块没有响应。
锁定的 7.0.2 插件调用了当前 LuCI 不提供的 `ui.confirm()`，在退出自动模式的
确认阶段抛错；另外，它读取 `fs.exec()` 返回值的 `rc`，而真实字段是 `code`，
会把已执行成功的命令误报为失败。

AP 机型钩子对锁定插件应用精确内容校验的补丁，改用 `ui.showModal()` /
`ui.hideModal()`，保留确认与取消行为，并按真实退出码判断结果。页面文件也纳入
实际 squashfs 与修补后构建源码的逐字节核对。补丁不改变驱动自动选择、温控曲线
或过热/传感器失效保护，不修改插件锁；上游内容变化时构建会要求重新审查补丁。

本机 8GB eMMC 实际走硬件 PWM。网页全速命令已达到 255/255，内核 PWM
实际配置为 39988/39994 ns；网页滑块 PWM 130 时实测回读一致，内核 PWM
为 20384/39994 ns，用户确认风声明显减小，随后已恢复原来的智能温控。
这些是控制接口与信号配置的验证；设备没有转速反馈，不能当作物理 RPM 测量。
热修复后若浏览器仍保留旧脚本，需清除该站点缓存或强制刷新。
已发布 Release 附件未替换，新固件仍需单独完成完整构建与镜像验收。

## 已知注意点

1. **Rust 双后端**：公共准备阶段安装 feeds 声明的 Rust 版本和目标标准库，复用 runner 工具链，
   并在恢复缓存后刷新路径；不再由 `Scripts/PRIVATE.sh` 安装或额外源码编译 host Rust。
2. **`kmod-airpi-gpio-fan` 与内核严格绑定**：模块带 vermagic，必须与本固件内核同批编译，不要单独
   拿 Release 里的 `.apk` 往其它固件上装。
3. **eMMC 机型**：按上游 `airpi_ap3000m` 画像走 `sysupgrade-tar`，分区 `PARTLABEL=rootfs`；刷机前
   请确认机器 eMMC 容量（8G/16G）与风扇驱动链路是否一致（插件会按 eMMC 容量自动切硬/软 PWM）。
4. **上游同步**：默认锁定源码、feeds 和插件。用 `latest` 试验更新后，再更新版本锁并验证。
   `config-resolution.json` 记录被 defconfig 丢弃的配置；必需包缺失会阻止构建通过。

## 真机联调记录（2026-10-25，设备 192.168.10.1）

首版固件刷入后「界面读不到 FM350」，在真机上逐层定位，全部已修进代码：

| # | 现象 | 根因 | 处理 |
| :--- | :--- | :--- | :--- |
| 1 | 插件状态页空白 | `fm350d` 用默认 `/dev/ttyUSB1`，而本机 FM350 在 `GTUSBMODE=41` 下的 AT 口是 USB 接口 `2-1:1.6` = `/dev/ttyUSB3`；守护自带的自动改选会把 `usb-usb2-2-1:1.6` 这种标识当路径写回 UCI 而被自身校验拒绝，于是永远停在哑口 | `Scripts/AP3000M/fm350-ap3000m` 首次开机按 USB 接口号反查 `/dev/ttyUSB*` 并写入 `fm350.main.at_port` |
| 2 | 有 IP/DNS 但 0 个包 | 插件默认 `cid=1`，而运营商 1 号承载是 `ims`（VoLTE），激活后只有 IPv6 链路本地；实际数据承载是 `cid=2`（`CMNET`） | 开机脚本解析 `AT+CGDCONT?`，挑一个非 `ims` 的承载写入 `fm350.main.cid` |
| 3 | 移动卡拨不上 | 插件默认 APN `ctnet`（电信） | 开机脚本按 IMSI 前缀选 `CMNET`/`CTNET`/`3GNET`，仅在 APN 仍为默认值时才覆盖 |
| 4 | `eth2` 收发计数 `tx_errors` 疯涨、`rx_packets=0` | 模组 RNDIS 端点一次性卡死（此前手动试错积累的状态） | 对模组 `AT+CFUN=1,1` 软重启 + 显式重设 `AT+GTUSBMODE=41`，重启后 RNDIS 恢复（`rx 147 / tx 243 / err 0`） |

修复后实测：

- `eth2` 拿到运营商地址（如 `10.66.79.163/24`），`gateway_mode=auto` 成功 ARP 到网关 `10.66.79.1`；
- 路由器 `ping -I <蜂窝IP> 223.5.5.5` 3/3、26 ms；
- LAN 侧（Windows 客户端）DNS / TCP 443 / HTTP 200 均正常；
- **整机重启后自动恢复**，无需人工干预。

## 构建缓存与 Release 清理

缓存的实际实现见[构建流程](BUILD-PIPELINE.md#缓存)：下载和 ccache 分别滚动保存，
工具链缓存要求严格匹配，恢复后刷新 Rust 路径。编译失败也可保留已经完成的 ccache，
取消的任务不保存；不能把某次耗时当作下次暖构建的保证。

`Auto-Clean.yml` 每天香港时间 05:21 运行，手动运行默认只预览，开启 APPLY 才执行删除。
按说明中的 `firmware-model` 标记分组；没有标记时识别 AP3000M/TR3000/C8-688 标签规则。
每个识别出的机型正式版和测试版各保留最近三个已发布 Release，保留 Git 标签；未识别的通用固件不自动删除。
发布失败时尝试立即删除本次 run/attempt 的流水线草稿。定时清理还会核对草稿的流水线标记、
机型工作流、提交及对应运行状态，仅回收已失败/取消且最后活动超过 24 小时的草稿。
人工草稿、仍在运行的发布、没有归属标记的旧草稿保留；不按 Release 的 `created_at` 计算年龄。

`Cache-Clean` 已移除定时触发。`MTK-ALL`、`OWRT-ALL`、`QCA-ALL`、`QCB-ALL`、`AIROHA-ALL`
也已移除清理完成后自动构建的触发，保留手动入口。


## 2026-10-28 运行逻辑修复

- OTA 的 `enabled=0` 关闭网页操作和定时检查；`auto_check=0` 只关闭定时检查。
  命令行手动操作仍允许。cron 保持唯一入口，每次执行读开关，重新启用不需要重装。
- 下载时把来自 GitHub 的仓库、标签、文件名、大小、SHA-256 保存到 `<TAG>.bin.json`。
  `upgrade --tag <TAG>` 优先核对本地镜像和这份记录，可断网回退；旧镜像缺少记录时，
  要先联网执行一次 `download --tag <TAG>` 获取并校验记录。回退仍必须通过 `sysupgrade -T`。
- 网页操作固定到页面显示的标签，下载/升级共用 flock，后台任务失败会在页面显示。
  “任务已启动”表示已进入后台校验，不等于已刷写。后台日志是
  `/tmp/ap3000m-ota-operation.log`；UCI `dir` 必须放在容量足够的存储上。
- RNDIS 自愈成功要求设备、IPv4、该接口的默认路由和有效收包计数均存在。
  开机、手动、定时自愈共用内核锁，避免重复复位；`rdnis_watch=0` 即时停止定时巡检。
- 新固件显式包含 `flock` 和 OTA 兼容标记；缺少兼容标记的旧固件应先整包升级。

这些修复有隔离行为测试和镜像内容检查；没有把它们当作新的真机刷写、拨号或散热验证。
