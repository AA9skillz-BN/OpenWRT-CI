## 1. 硬件（全部实机取过证）

| 项 | 值 | 来源 |
|---|---|---|
| 型号 / compatible | `NRadio C8-688` / `nradio,c8-688`（原厂 model 是 `HC-WT9104`） | 实机 device-tree |
| SoC / 内存 | MT7981B / 1 GB | DTS |
| 存储 | eMMC 8 GB，GPT：`kernel`(32M) `rootfs`(256M) **`kernel_2nd`(128M)** **`rootfs_2nd`(6.56G)** `factory`(1M) `bdinfo`(1M) `u-boot-env`(512K) `fip`(2M) `app_data`(256M) | `cat /proc/partitions` |
| 交换机 | MT7531（DSA，mdio 31）：`lan1~lan3` 千兆 + `lan4` 2.5G | 实机 mdio |
| 2.5G PHY | **两片 GPY211 `0x67c9de0a`，分别在 mdio 5 与 mdio 15** | `/sys/bus/mdio_bus/devices` |
| 5G 上行 | **`eth1`**（gmac1 + mdio15 那片），实测 `Speed: 2500Mb/s`，DHCP 拿 `192.168.8.101` | `ip -br addr` + `ethtool` |
| 模组 | **TD Tech MT5700M-CN**（USB `3466:3301`，ttyUSB0~3），**AT over TCP `192.168.8.1:20249`** | `lsusb` + `nc` |
| 风扇 | PWM0（`platform/10048000.pwm`，period 40µs），`fan-hw`=GPIO27、`fan-fg`=GPIO28 | `/sys/kernel/debug/pwm` + gpio |
| 灯 | status=10、5G=11、4G=12、**wifi=34**（全低有效） | `/sys/kernel/debug/gpio` |
| 键 / 电源 | reset=1、wps=9；`cpe-pwr`=31（低有效）；`cpe-sel0/1`=29/30；switch reset=39 | 同上 |
| WiFi 校准 | `factory` 分区前 4 KiB，chip id `0x7981`；**offset 4 的 MAC 是占位值** | `hexdump` |
| 真实 MAC | `bdinfo` 分区文本：`fac_mac = FC:83:C6:14:9F:A0` | `dd \| strings` |
| U-Boot env | `u-boot-env` 分区 offset 0：CRC32 + `boot_system=0` + `bootdelay=2`，**单份无冗余** | `hexdump` |

> ⚠️ **坑**：in-tree 的 `mt7981b-nradio-c8-668gl.dts` 把第二个 2.5G PHY 写在 `reg = <21>`，
> 这台机实际是 **15**。照抄会导致 `eth1`（5G 上行）起不来。

## 3. 刷机（只动第二系统槽）

### 前提

1. **关掉"存储扩展"**（它占着 `rootfs_2nd`；开着时原厂连烧录都会拒绝）。
   ```sh
   mount | grep mmcblk0p9
   umount /dev/mmcblk0p9
   rm -f /etc/nradio_storage_expand_enabled
   ```
2. **备份三个小分区**（丢了就没了）：
   ```sh
   mkdir -p /tmp/c8bak
   dd if=/dev/mmcblk0p2 of=/tmp/c8bak/uboot-env.bin
   dd if=/dev/mmcblk0p3 of=/tmp/c8bak/factory.bin
   dd if=/dev/mmcblk0p4 of=/tmp/c8bak/bdinfo.bin
   ```

### 两步法（写盘与切系统分离）

原厂烧录器 `/usr/bin/sysupgrade-opensource` **只写 `kernel_2nd` / `rootfs_2nd`**，
写完**不改 `boot_system`、不重启**：

```sh
# ① 只写不切
/usr/bin/sysupgrade-opensource -f /tmp/firmware.img

# ② 手动重启 —— 应该照常进原厂
reboot

# ③ 回 SSH 验写入结果
hexdump -C -n 8 /dev/mmcblk0p8     # → d0 0d fe ed (FIT)
hexdump -C -n 4 /dev/mmcblk0p9     # → 68 73 71 73 ("hsqs" = squashfs)

# ④ 切系统（单程票，之前所有步骤都可逆）
ubenv -s boot_system -v 1 && reboot
```

前三步随便折腾都能回原厂；**第④步之后如果新系统起不来，就只能接串口**（UART0，
`serial@11002000`，115200 8N1，3.3V）进 U-Boot 把 `boot_system` 改回 0。

## 4. 回退

固件里带 `c8-boot-official`（依赖 `uboot-envtools` + 首启自动探测出的 `/etc/fw_env.config`）：

```sh
c8-boot-official status      # 看当前 boot_system
c8-boot-official official    # 写 0 + 重启 → 回原厂
c8-boot-official second      # 写 1 + 重启 → 回本系统
```

原理：先 `fw_printenv` 只读校验，读不出来就绝不动手（避免写坏 env）。

## 6. 已知限制

- **没有原厂 APP**：NR-OS 的蜂窝页、4 卡切换、IP 透传、风扇/灯面板都没有；5G 管理用 `luci-app-mt5700m`。
- **4 个 SIM 槽不自动切**：原厂用 GPIO29/30 组合选卡，目前只是把 `cpe-sel0/1` 导出成 gpio-export。
- **2.4G 未验证**：原厂跑 MTK SDK `mt_wifi`，不注册 mac80211，无法提前验证 mt76 是否吃这份 eeprom。
- **WiFi MAC 走 UCI 覆盖**（`c8-wifi-mac`，START=19），不改 flash；eeprom 里的占位值保持原样。
- **风扇曲线是自研的**（原厂 `fanctrl` 在 75℃ 时占空比为 0），默认 45/55/65/75℃ → 0/90/150/205/255。

## 7. 排障

| 现象 | 先查 |
|---|---|
| 构建红在 private.sh | 上游 `filogic.mk`/`02_network` 改了锚点，按日志里报的名字改 |
| 构建绿但没产物 | manifest 闸门会先红；看是不是 `luci-app-mt5700m` 被 defconfig 丢了 |
| 刷完回原厂 | `ubenv -s boot_system -o 1` 看是不是还 0（烧录器本来就不改它） |
| 起来了但没网 | `ip -br addr` 看 `eth1` 有没有 192.168.8.x；`nc 192.168.8.1 20249` 发个 `ATI` |
| 2.5G 口不通 | `ethtool lan4`；`dmesg \| grep -i gpy`；确认 DTS 里是 `reg = <5>` 和 `<15>` |
| WiFi 起不来 | `dmesg \| grep -i mt76`；`iw dev`；`cat /etc/config/wireless` 看 macaddr |
| 风扇不转 | `cat /sys/class/hwmon/hwmon*/name`（=pwmfan）、`/etc/init.d/c8-fan restart`、`logread -e c8-fan` |
| 想回原厂但 `fw_printenv` 报 CRC | `/etc/fw_env.config` 里的 0x8000 改成 0x4000 或 0x10000 |


## 2026-10-28 升级与散热保护

机型钩子给上游平台脚本增加 C8 专用的检查、升级、配置复制分支；其它机型分支保留。
适配器发现上游新增 C8 支持或修改分派结构时停止构建，要求重新审查。
仅当 `kernel_2nd` 和 `rootfs_2nd` 分别对应块设备 `/dev/mmcblk0p8`、`/dev/mmcblk0p9`
时才允许升级；镜像成员、大小和空间也必须通过校验。不会使用原厂 `rootfs_data` 作为升级数据分区。
最终 squashfs 校验同时核对适配后的平台脚本和 `/lib/upgrade/c8-688.sh`。

温度缺失、非数字或异常读数不会关闭风扇，改为全速并记录日志；有效温区按最高 SoC 温度调速。
WiFi MAC 增量交给上游 `macaddr_add` 处理进位。这些行为已有隔离测试，实际分区布局、
配置恢复和温度传感器名称仍应在真机首次升级时核对；未进行新的真机刷写或散热测试。
