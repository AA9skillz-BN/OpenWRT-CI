## 1. 硬件（全部实机取过证）

| 项 | 值 | 来源 |
|---|---|---|
| 型号 / compatible | `NRadio C8-688` / `nradio,c8-688`（原厂 model 是 `HC-WT9104`） | 实机 device-tree |
| SoC / 内存 | MT7981B / 1 GB | DTS |
| 存储 | eMMC 8 GB，GPT：`kernel`(32M) `rootfs`(256M) **`kernel_2nd`(128M)** **`rootfs_2nd`(6.56G)** `factory`(1M) `bdinfo`(1M) `u-boot-env`(512K) `fip`(2M) `app_data`(256M) | `cat /proc/partitions` |
| 交换机 | MT7531（DSA，mdio 31）：`lan1~lan3` 千兆 + `lan4` 2.5G | 实机 mdio |
| 2.5G PHY | **GPY211，MDIO 0x05 与 0x15（十进制 5 与 21）**；原厂 DTB 声明 ID `0x67c9de0a`，新系统地址 0x05 的 C45 实读为 `0x67c9de10` | 原厂 kernel DTB + 新系统 MDIO sysfs |
| 5G 上行 | **`eth1`**（gmac1 + MDIO 0x15），原厂实测 `Speed: 2500Mb/s`，DHCP 拿 `192.168.8.101` | 原厂 `ip -br addr` + `ethtool`；修正 DTS 后仍需新系统实机复核 |
| 模组 | **TD Tech MT5700M-CN**（USB `3466:3301`，ttyUSB0~3），**AT over TCP `192.168.8.1:20249`** | `lsusb` + `nc` |
| 风扇 | PWM0（`platform/10048000.pwm`，period 40µs），`fan-hw`=GPIO27、`fan-fg`=GPIO28 | `/sys/kernel/debug/pwm` + gpio |
| 灯 | status=10、5G=11、4G=12、**wifi=34**（全低有效） | `/sys/kernel/debug/gpio` |
| 键 / 电源 | reset=1、wps=9；`cpe-pwr`=31（低有效）；`cpe-sel0/1`=29/30；switch reset=39 | 同上 |
| WiFi 校准 | `factory` 分区前 4 KiB，chip id `0x7981`；**offset 4 的 MAC 是占位值** | `hexdump` |
| 真实 MAC | `bdinfo` 分区文本：`fac_mac = FC:83:C6:14:9F:A0` | `dd \| strings` |
| U-Boot env | p2 `u-boot-env`，offset 0、大小 `0x80000`，CRC32 + 环境文本，**单份无冗余** | 原厂备份 + 现机完整 p2 的 CRC32 计算，`fw_printenv -c` 只读复核 |

> **PHY 地址必须区分进制**：原厂 kernel DTB 确认为 `reg = <0x15>`，等于十进制 `<21>`。
> sysfs 的 `mdio-bus:15` 和 DTS 节点名 `ethernet-phy@15` 都用十六进制。
> 早期适配误写 `<15>`，实际访问 0x0f，导致 PHY 无驱动、GPIO8 保持复位、`eth1` 报
> `could not attach PHY: -22`。镜像验收现检查实际 FIT DTB 的地址、连接、模式和复位脚。

## 3. 刷机（只动第二系统槽）

### 前提

1. **关掉"存储扩展"**（它占着 `rootfs_2nd`；开着时原厂连烧录都会拒绝）。
   ```sh
   mount | grep mmcblk0p9
   umount /dev/mmcblk0p9
   rm -f /etc/nradio_storage_expand_enabled
   ```
2. **备份三个小分区**（丢了就没了）：
   ```sh
   mkdir -p /tmp/c8bak
   dd if=/dev/mmcblk0p2 of=/tmp/c8bak/uboot-env.bin
   dd if=/dev/mmcblk0p3 of=/tmp/c8bak/factory.bin
   dd if=/dev/mmcblk0p4 of=/tmp/c8bak/bdinfo.bin
   ```

### 两步法（写盘与切系统分离）

原厂烧录器 `/usr/bin/sysupgrade-opensource` **只写 `kernel_2nd` / `rootfs_2nd`**，
写完**不改 `boot_system`、不重启**：

```sh
# ① 只写不切
/usr/bin/sysupgrade-opensource -f /tmp/firmware.img

# ② 手动重启 —— 应该照常进原厂
reboot

# ③ 回 SSH 验写入结果
hexdump -C -n 8 /dev/mmcblk0p8     # → d0 0d fe ed (FIT)
hexdump -C -n 4 /dev/mmcblk0p9     # → 68 73 71 73 ("hsqs" = squashfs)

# ④ 切系统（单程票，之前所有步骤都可逆）
ubenv -s boot_system -v 1 && reboot
```

前三步随便折腾都能回原厂；**第④步之后如果新系统起不来，就只能接串口**（UART0，
`serial@11002000`，115200 8N1，3.3V）进 U-Boot 把 `boot_system` 改回 0。

## 4. 回退

固件里带 `c8-boot-official`（依赖 `uboot-envtools` + 首启自动探测出的 `/etc/fw_env.config`）：

```sh
c8-boot-official status      # 看当前 boot_system
c8-boot-official official    # 写 0 + 重启 → 回原厂
c8-boot-official second      # 当前仍运行第二系统时，选择下次继续进第二系统并重启
```

原理：先 `fw_printenv` 只读校验，读不出来就绝不动手（避免写坏 env）。
已从当前实机读取完整 p2，独立 CRC32 核对确认环境长度为 `0x80000`，
并以临时配置只读复核 `boot_system=1`。旧探针漏掉这一长度，留下的 `0x8000`
配置会报 Bad CRC。新探针先检查 `0x80000`，只原子安装 CRC 有效且值为 0/1 的配置；
全失败时保留原配置，不写环境分区。此只读核对不等于已经执行过系统切换。

Aurora 主题下进入 **系统 → 固件升级**，可检查 C8 正式渠道、下载并校验、
保留/清空配置升级、从已下载版本回退，以及确认后切回第一系统。
OTA 只写第二系统；切回第一系统只设置启动环境并重启，不重刷原厂固件。
原厂系统需要仍然完好，切回后的地址和密码按原厂系统配置。
此辅助程序只在第二系统通过守卫后工作；回到原厂后需使用原厂自己的启动选择入口，
不能把第二系统里的命令当成原厂也已安装的工具。

命令行入口：

```sh
c8-688-ota check
c8-688-ota upgrade --keep --yes
c8-688-ota upgrade --tag <正式版标签> --keep --yes
c8-688-ota official --yes
```

下载、升级、独立 CLI 更新和系统切换共用锁。板型、第二系统启动参数、
p2/p8/p9 分区标签、env 配置与 CRC、写后读回任一检查失败均拒绝切换。
每天自动检查仅更新提示，默认不自动刷写。BUILD_ONLY 固件尚无对应公开 Release，
不能把网页“当前版本与最新发布不同”直接当作应升级的结论。

## 6. 已知限制

- **没有原厂 APP**：NR-OS 的蜂窝页、4 卡切换、IP 透传、风扇/灯面板都没有；5G 管理用 `luci-app-mt5700m`。
- **4 个 SIM 槽不自动切**：原厂用 GPIO29/30 组合选卡，目前只是把 `cpe-sel0/1` 导出成 gpio-export。
- **2.4G 未验证**：原厂跑 MTK SDK `mt_wifi`，不注册 mac80211，无法提前验证 mt76 是否吃这份 eeprom。
- **WiFi MAC 走 UCI 覆盖**（`c8-wifi-mac`，START=19），不改 flash；eeprom 里的占位值保持原样。
- **风扇管理**：移植 `LianXia233/luci-app-h5000m-fancontrol` 的 LuCI 页面和 Rust 控制器，
  提供自动、手动 PWM 和内核控制模式。旧 `c8-fan` 只做代理，不再启动另一个 PWM 写入循环。
  默认以 CPU 温度控制，保留内核冷却映射、hot/critical 保护；CPU 温度缺失或达到 75℃时
  手动模式也全速。内核要求的最低占空比可能高于手动请求值，页面显示实际回读值，不能当作实测 RPM。
  C8 的 `active-low/med/high` trip 名称已适配，不使用 H5000M 的旧阈值作正常下限。
  不直连模组串口；当前 MT5700M 插件没有 H5000M 的 8765 RPC 桥，模组温度缺失时显示未知。
  该包保留审查后的 JS 原文，便于实际 squashfs 对照源码；其它 LuCI 包的压缩设置不变。

## 7. 排障

| 现象 | 先查 |
|---|---|
| 构建红在 private.sh | 上游 `filogic.mk`/`02_network` 改了锚点，按日志里报的名字改 |
| 构建绿但没产物 | manifest 闸门会先红；看是不是 `luci-app-mt5700m` 被 defconfig 丢了 |
| 刷完回原厂 | `ubenv -s boot_system -o 1` 看是不是还 0（烧录器本来就不改它） |
| 起来了但没网 | `ip -br addr` 看 `eth1` 有没有 192.168.8.x；`nc 192.168.8.1 20249` 发个 `ATI` |
| 2.5G 口不通 | `ethtool lan4`；`dmesg \| grep -i gpy`；确认实际 DTB 的 PHY reg 是 `0x05` 和 `0x15`（十进制 5、21） |
| WiFi 起不来 | `dmesg \| grep -i mt76`；`iw dev`；`cat /etc/config/wireless` 看 macaddr |
| 风扇不转 | `cat /sys/class/hwmon/hwmon*/name`（=pwmfan）、`h5000m-fancontrol status json`、`logread -e h5000m-fancontrol` |
| 想回原厂但 `fw_printenv` 报 CRC | 新版 `c8-env-detect` 需发现有效 CRC；已核本机配置为 `/dev/mmcblk0p2 0x0 0x80000`，不能绕过 CRC 强写 |

### USB 蜂窝上网恢复的实机范围

首次第二系统实机测试确认，旧镜像的 PHY 地址错误使板载 `eth1` 无法挂接；
MT5700M 插件则只管理 USB 网卡，不会用 `eth1` 替代 USB 拨号。
原厂的 Ethernet 自动拨号配置也不能直接当成 USB 配置使用。

这台设备已验证的临时替代路径是 USB NCM：先备份 UCI 和模组原始设置，
通过插件的事务接口切换为 Host dialing over USB，再将模组 interface mode 改为
`2`（USB router + Ethernet router），重启**模组**后重新发现 USB/AT 设备。
仅切换 profile 时，mode 1 曾出现 DHCP 地址与 IPv6 可用、IPv4 网关 ARP 不响应；
mode 2 重启后 IPv4 的 DHCP、DNS、HTTPS 和真实 LAN 转发均通过。
这证明了此机的恢复方法，未证明所有模组都需要修改 interface mode。

USB IPv6 共用模组的 /64 前缀时，另需核对默认路由和 NDP：本机设置
`network.MT5700Mv6.sourcefilter=0`，并让 `dhcp.MT5700Mv6`（interface 为
`MT5700Mv6`、master 为 `1`）与 `dhcp.lan` 的 `ndp` 均为 `relay`，保留原有
LAN RA/DHCP、DNS、metric 和防火墙策略。服务重启后，路由器和实际 Wi-Fi
电脑的 IPv4/IPv6 HTTPS、DNS、递增收发计数均通过。不要把这组 USB 设置无条件
应用于另一个 IPv6 上行、用户自设的路由策略或其它机型。

当前 USB 协商速率为 480 Mbps，此路径有速度上限；板载 2.5G 路径需部署修正
PHY 地址的新镜像后再单独验收。已有 Release 的镜像不会因仓库 DTS 修正而改变。


## 2026-10-28 升级与散热保护

机型钩子给上游平台脚本增加 C8 专用的检查、升级、配置复制分支；其它机型分支保留。
适配器发现上游新增 C8 支持或修改分派结构时停止构建，要求重新审查。
仅当 `kernel_2nd` 和 `rootfs_2nd` 分别对应块设备 `/dev/mmcblk0p8`、`/dev/mmcblk0p9`
时才允许升级；镜像成员、大小和空间也必须通过校验。不会使用原厂 `rootfs_data` 作为升级数据分区。
最终 squashfs 校验同时核对适配后的平台脚本和 `/lib/upgrade/c8-688.sh`。

温度缺失、非数字或异常读数不会关闭风扇，改为全速并记录日志；有效温区按最高 SoC 温度调速。
WiFi MAC 增量交给上游 `macaddr_add` 处理进位。这些行为已有隔离测试，实际分区布局、
配置恢复和温度传感器名称仍应在真机首次升级时核对；未进行新的真机刷写或散热测试。
