# TR3000 512MB 固件构建与维护

> 与 AP3000M、C8-688 共用 `.github/workflows/DEVICE-CORE.yml`，直接通过独立 bash
> 进程执行 `Scripts/TR3000-512/private.sh`。构建阶段和维护方法见
> [构建流程](BUILD-PIPELINE.md)。

## 适用设备与源码

- Cudy TR3000 v1，512MB 闪存硬改版，设备标识 `cudy,tr3000-v1`。
- 源码：<https://github.com/VIKINGYFY/immortalwrt>，分支 `owrt`（MTK 专用，与原独立版基座一致）。
- 仅适用于已验证的分区：UBI 起点 `0x5c0000`，长度 `0x1da40000`；页大小 2048 字节、擦除块 128KiB。
- 不适用于未经核对的原厂、256MB 或其他 U-Boot 分区布局。

## 默认功能与登录

- 后台地址：<http://192.168.6.1>，用户名 `root`；首次登录设置密码。
- 主机名 `TR3000`、WiFi `TR3000 / 12345678`、Aurora 主题、默认简体中文。
- LuCI 基础、防火墙、软件包管理、Aurora 配置、TurboACC、ttyd 均选择简体中文包。
- ttyd Web 终端：后台“系统 → 终端”，用路由器系统账号登录（浏览器里直接开 root shell）。
- mt76 开源无线驱动、TurboACC 管理界面、软件及硬件 Flow Offloading、WED。
- OpenClash（Mihomo 内核与订阅需刷机后另外下载、导入）。
- F50 USB 上网：RNDIS、CDC Ethernet、CDC NCM 驱动由 `Config/Features/usb.txt` 提供。

## F50 USB 上网（自动接入）

**旧固件的问题**：`network.F50` 被写死成 `device='eth2'`。`eth2` 只是某一次 USB 枚举顺序的产物，
换线、换口、换设备或重新枚举后名字一变，接口就变成「网络设备不存在」，DHCP 永远起不来 ——
表现为「F50 自己有网，但 TR3000 发出的 WiFi 一点网都没有」。另外该接口**没有被加入任何防火墙区**，
即便拿到地址也不会做 NAT。

**现在的做法**：`/etc/tr3000-usbwan.sh` 按 USB 总线实时探测，按当前枚举结果更新设备绑定：

1. 只有首次创建 `network.f50` 时，才设置 DHCP、`metric 10`、`peerdns=0` 和三个公共 DNS；
2. 已有协议、地址、DNS、metric 以及 `disabled` / `auto` 开关保留，关闭自动启动时不拉起接口；
3. 旧 `network.F50` 改名为 `f50`，保留配置并迁移防火墙区域中的旧名称；
4. 保留已有的防火墙区域；未加入区域时补入 `wan`，修正旧的带引号 NAT 值，保留明确关闭的 NAT；
5. 启动接口，应用 RPS；仅防火墙配置变化时重载防火墙。

公共 DNS 是首次创建时的默认值，不会在后续热插拔时覆盖用户设置。下面的联调记录描述的是当时特定设备与网络的情况。

触发点三处：net hotplug（插拔）、`/etc/init.d/tr3000-usbwan`（开机）、首个开机脚本（兜底）。

排查命令（ttyd 里）：

```sh
ls /sys/bus/usb/devices                  # 只有 usb1/usb2 根 hub = USB 口上没有任何设备
ls /sys/class/net                        # 看 USB 网卡叫什么（usb0/eth2/…）
cat /etc/config/network | sed -n '/f50/,/^$/p'
uci show firewall | grep -E "zone.*wan|network"
logread -e tr3000-usbwan                 # 脚本自己的日志
```

若是 `ls /sys/bus/usb/devices` 里连 `1-1` 都没有，那不是固件问题：换一根**确认能传数据**的 USB 线、
确认 F50 的「USB 网络共享」已开、并保证 F50 供电充足（F50 走 5G 时功耗较大）。

## 构建与下载

1. 进入 Actions，选择 `TR3000`。
2. 默认使用 `SOURCE_MODE=locked` 和版本锁中的 `VIKINGYFY/immortalwrt@owrt`。
   试用其他 `SOURCE` / `BRANCH` 时显式选择 `latest`，经验证后再更新版本锁。
3. 先用 `TEST=true` 检查配置，再用 `BUILD_ONLY=true` 完整编译并校验固件。
4. 需要发布时关闭 TEST 和 BUILD_ONLY。编译通过后，独立发布 job 下载本次 Artifact，
   复核校验和，再上传 draft Release 并公开；不再事后下载或裁剪“最新 Release”。

校验要求来自 `Profiles/TR3000-512.json`，包括必需软件包、tar 结构和设备元数据，
并检查实际 FIT 中的 DTB 分区，以及 squashfs 内的关键脚本、启动链接和构建标签。
附件包含 sysupgrade、实际配置、manifest、校验和与版本及校验证据。
标签包含机型、源码、分支、时间、run ID 和 attempt；非 main 分支额外使用 `preview-` 前缀。

`Auto-Clean.yml` 按型号和正式 / 测试渠道分别保留最近 3 个已发布 Release，每天香港时间 05:21 执行。

## 升级与验证

使用名称包含 `cudy_tr3000-v1-squashfs-sysupgrade`、后缀为 `.bin` 的镜像。
升级前备份配置、核对 sha256，执行 `sysupgrade -T /tmp/实际固件文件名.bin`，通过后再升级。
首次跨源码升级建议不保留配置。

默认 LAN 地址在构建期设置；已删除强制重设 LAN、主题和加速选项的自定义首启脚本。
保留配置升级时，这些旧脚本不再覆盖用户选择；F50 的自动接入行为见下方注意点。

## 编译缓存

由 `DEVICE-CORE.yml` 管理独立的下载、ccache 和严格匹配的工具链缓存，使用
下载/ccache 的 `wrt-v2-tr3000-512-` 命名空间和按实际依赖共享的 v3 工具链命名空间。
具体恢复与保留策略见[构建流程](BUILD-PIPELINE.md#缓存)。

## 已知注意点

1. **分区补丁是硬门槛**：`patch-layout.sh` 若因上游 DTS 变动而断言失败，构建会直接中止，
   这是故意的——镜像大小/UBI 布局不对的固件刷进 512MB 机器会变砖。
2. **保留配置升级**：旧 `network.F50` 会迁移为 `f50` 并保留设置；已有 `f50` 的协议、DNS、metric、停用开关和防火墙区域保留，设备绑定按 USB 枚举结果更新。
3. **固件体积**：基础与功能片段保留 Samba、Btrfs、NVMe、OpenVPN 等选择。
   上游包名消失会记录到 `config-resolution.json`；必需包丢失会阻止构建通过。

## 真机联调记录（2026-10-25，设备 192.168.6.1）

F50（ZTE，USB 共享）从「完全没网」到「全链路通」踩过的坑，都是真实量到的：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | F50 自己有网，TR3000 发的 WiFi 一点网都没有 | `/sys/bus/usb/devices` 只有 `usb1`/`usb2` 两个根 Hub —— 那根 USB 线是**纯充电线**（无 D+/D-），压根没枚举出设备 | 换一根确认能传数据的线 |
| 2 | 换线后 USB 枚举、拿到 IP，但 `ping 223.5.5.5` 100% 丢包，看着像没网 | **这条链路上 ICMP 被屏蔽**。同时 `curl http://223.5.5.5/` 返回 404（0.07s），TCP 一直是通的 | 别用 ping 判断生死，用 `curl`/TCP 复测 |
| 3 | **「没有下载速度」**：偶尔网页能打开，镜像站却直接 `Could not resolve host` | F50 自带的 DNS `192.168.0.1` 对 CNAME 链（`mirrors.aliyun.com` → `w.alikunlun.com`）只回 CNAME、不回 A 记录，客户端拿不到 IP；直连 114 查同一域名 10/10 成功 | 固件改成 `peerdns=0` + 三个公共 DNS，实测解析 10/10、下载 5.2 MB/s |
| 4 | 早期 `network.F50.device='eth2'` 报「网络设备不存在」 | 设备名写死，换线/重新枚举后名字一变就废 | `tr3000-usbwan.sh` 按 USB 总线实时探测 |

验证通过的实测值：

```
eth2: 192.168.0.171/24, default via 192.168.0.1
ping 192.168.0.1        → 0.6 ms
curl http://223.5.5.5/  → HTTP 404, 0.07 s      # TCP 出网
curl --interface 192.168.6.1 http://223.5.5.5/ → 404, 2.5 s   # LAN→NAT 验证
客户端出口 IP            → 183.194.125.118（中国移动·上海，F50 的 5G 出口）
DNS 解析 10/10           → 114 / 223.5.5.5 / 119.29.29.29
镜像站下载 38.5 MB       → 7.3 s，5.25 MB/s（约 42 Mbps）
```

> 排查提示：客户端「上不了网」先分清是**解析失败**还是**转发失败**。
> 路由器上 `curl --interface 192.168.6.1 http://223.5.5.5/` 能 404，就说明 NAT 与转发没问题，问题只剩 DNS。
