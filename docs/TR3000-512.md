# TR3000 512MB 固件构建与维护

> 与 AP3000M 共用 `.github/workflows/DEVICE-CORE.yml`，直接通过独立 bash
> 进程执行 `Scripts/TR3000-512/private.sh`。构建阶段和维护方法见
> [构建流程](BUILD-PIPELINE.md)。

## 适用设备与源码

- Cudy TR3000 v1，512MB 闪存硬改版，设备标识 `cudy,tr3000-v1`。
- 源码：<https://github.com/VIKINGYFY/immortalwrt>，分支 `owrt`（MTK 专用，与原独立版基座一致）。
- 仅适用于已验证的分区：UBI 起点 `0x5c0000`，长度 `0x1da40000`；页大小 2048 字节、擦除块 128KiB。
- 不适用于未经核对的原厂、256MB 或其他 U-Boot 分区布局。

## 默认功能与登录

- 后台地址：<http://192.168.6.1>，用户名 `root`；首次登录设置密码。
- 主机名 `TR3000`、WiFi `TR3000 / 12345678`、Aurora 主题、默认简体中文。
- LuCI 基础、防火墙、软件包管理、Aurora 配置、TurboACC、ttyd 均选择简体中文包。
- ttyd Web 终端：后台“系统 → 终端”，用路由器系统账号登录（浏览器里直接开 root shell）。
- mt76 开源无线驱动、Arthur TurboACC 管理界面、软件及硬件 Flow Offloading、WED。
- OpenClash 内置官方 ARM64 静态 Mihomo（Meta）内核；订阅仍需自行导入，默认不启用代理。
  `PLUGIN_MODE=latest` 解析官方最新稳定版，`locked` 使用 `Profiles/openclash-core.lock.json`。
  构建校验压缩包大小/SHA-256、静态 ELF 架构，实际镜像核对内核、来源记录与许可证；
  来源记录位于 `/usr/share/openclash/tr3000-core.json`，同时保留在构建 Artifact。
- F50 USB 上网：RNDIS、CDC Ethernet、CDC NCM 驱动由 `Config/Features/usb.txt` 提供。

## F50 经转网口接有线 WAN

F50 经转网口接 TR3000 **WAN 网口**时，使用 `network.wan` 的 `eth0` DHCP，
不是直接 USB 插入 TR3000 的 `f50` 接口。本机实测出现过开机千兆链路已建立、
DHCP 持续发送但 eth0 接收包始终为零；单次 down/up 可恢复。尚不能据此区分
PHY/驱动与上游转网口互操作问题。

`tr3000-wan-boot-guard` 只在开机前 180 秒观察：至少等到 60 秒，确认默认 DHCP WAN
绑定 eth0、没有 IPv4 地址、未桥接、链路已连接且持续 10 秒发包而 RX 为零，才复位一次。
每次开机最多一次，不修改 UCI、MAC、DNS、防火墙或其他接口；已有接收、静态/自定义 WAN、
停用接口和正常运行中的网络不复位。可用 `network.wan.boot_rx_recovery=0` 关闭。
日志标签为 `tr3000-wan-boot-guard`。这是针对已复现现象的自动恢复，不能据此认定底层硬件原因已消除。

## F50 USB 上网（自动接入）

**旧固件的问题**：`network.F50` 被写死成 `device='eth2'`。`eth2` 只是某一次 USB 枚举顺序的产物，
换线、换口、换设备或重新枚举后名字一变，接口就变成「网络设备不存在」，DHCP 永远起不来 ——
表现为「F50 自己有网，但 TR3000 发出的 WiFi 一点网都没有」。另外该接口**没有被加入任何防火墙区**，
即便拿到地址也不会做 NAT。

**现在的做法**：`/etc/tr3000-usbwan.sh` 按 USB 总线实时探测，按当前枚举结果更新设备绑定：

1. 只有首次创建 `network.f50` 时，才设置 DHCP、`metric 10`、`peerdns=0` 和三个公共 DNS；
2. 已有协议、地址、DNS、metric 以及 `disabled` / `auto` 开关保留，关闭自动启动时不拉起接口；
3. 旧 `network.F50` 改名为 `f50`，保留配置并迁移防火墙区域中的旧名称；
4. 保留已有的防火墙区域；未加入区域时补入 `wan`，修正旧的带引号 NAT 值，保留明确关闭的 NAT；
5. 启动接口，应用 RPS；仅防火墙配置变化时重载防火墙。

公共 DNS 是首次创建时的默认值，不会在后续热插拔时覆盖用户设置。下面的联调记录描述的是当时特定设备与网络的情况。

触发点三处：net hotplug（插拔）、`/etc/init.d/tr3000-usbwan`（开机）、首个开机脚本（兜底）。

排查命令（ttyd 里）：

```sh
ls /sys/bus/usb/devices                  # 只有 usb1/usb2 根 hub = USB 口上没有任何设备
ls /sys/class/net                        # 看 USB 网卡叫什么（usb0/eth2/…）
cat /etc/config/network | sed -n '/f50/,/^$/p'
uci show firewall | grep -E "zone.*wan|network"
logread -e tr3000-usbwan                 # 脚本自己的日志
```

若是 `ls /sys/bus/usb/devices` 里连 `1-1` 都没有，那不是固件问题：换一根**确认能传数据**的 USB 线、
确认 F50 的「USB 网络共享」已开、并保证 F50 供电充足（F50 走 5G 时功耗较大）。

## IPv6 通告优先级

F50 只提供 /64、没有 DHCPv6-PD 时，TR3000 可以中继 IPv6 通告。当前 odhcpd
中继会保留上游的高优先级，`dhcp.lan.ra_preference` 只影响服务端模式，不能修正这一情况。
双网卡客户端因此可能让 TR3000 Wi-Fi 抢占有线 IPv6 默认路由。

TR3000 专属的 `/etc/nftables.d/90-tr3000-ra-medium.nft` 由 firewall4 自动加载：
仅将发往 `br-lan`、来自链路本地地址、Hop Limit 255、Code 0 的本机 IPv6 RA 中
高优先级改为普通级别；普通和低优先级通告保持原样。规则显式修正 ICMPv6 校验和，
保留前缀、DNS、MTU、M/O 标志及中继功能，不修改客户端网卡、IPv4 或路由器 UCI 配置。
这使 TR3000 的普通通告优先级与 AP3000M 实测行为一致；客户端最终选路仍取决于自身接口 metric。

文件随 TR3000 overlay 安装，profile 要求实际 squashfs 内的文件与源码逐字节一致，
并要求 `firewall4`、`nftables-json` 出现在最终 manifest。Linux 测试在独立网络命名空间
实发报文，检查校验和进位、作用范围以及重新加载。要恢复上游高优先级，将该文件移到
不以 `.nft` 结尾的路径后重载防火墙；升级时注意保留这项选择。

2026-11-21 真机配置验证：TR3000 的 Windows IPv6 默认路由 metric 从 16 变为 256，
与 AP3000M 相同；现有电脑同时连接有线和 TR Wi-Fi 时 IPv4/IPv6 均选有线。
强制经 TR 的客户端 IPv4/IPv6 HTTPS 均通过，防火墙重载后仍生效，电脑配置未改动。
此记录验证了设备上的同一规则；新编译镜像及整机重启的验收应单独记录。

## TurboACC

使用 [Arthur97172/luci-app-turboacc](https://github.com/Arthur97172/luci-app-turboacc)，
取代 chenmozhijin 版；上游版本 1.3.2-r1，经本仓库适配后的包版本为 1.3.2-r2。
前端为 JavaScript，后端为 ucode，沿用现有 firewall4、内核及其 SONiC FullCone 实现。
不额外引入 SFE、NSS、厂商 HNAT 或替换防火墙补丁。

首次配置仍默认软件/硬件 Flow Offloading、WED 和 BBR。实际后端不支持的选项由能力检测
关闭。VIKINGYFY 的 SONiC FullCone 使用布尔防火墙选项；适配层将 Arthur 的模式 2 正确
转换为防火墙值 1，不能把模式编号直接写入布尔选项。

保留配置升级时，适配层迁移旧版 `sw_flow`、`hw_flow`、`sfe_flow`、`hw_wed`、
`bbr_cca`、`fullcone_nat`，然后删除这些失效键；新格式已有选择优先，明确关闭的功能不重新开启。
保留使用相同字段的 `fullcone6`。删除旧版持久 ucitrack init 记录，只保留新版 JSON exec
触发器；自定义 exec 及其他服务的触发器不删除。新版在选中 BBR 后按需加载模块，移除旧
`tr3000-bbr` 独立服务，避免两套脚本互相覆盖。

`ucitrack` 是 `luci-base` 安装的服务，不是独立软件包。依赖其所属的 `luci-base`，
并在实际镜像中核对 `/etc/init.d/ucitrack` 的源码字节、执行权限及 `S80ucitrack` 启动入口。

首启清理仅删除已知旧 Lua 控制器/页面、旧首启脚本和 TR BBR 启停链接，不执行旧版
会改写防火墙/DNS 的 stop。镜像门禁核对新版配置、JS/CSS、ucode、菜单、ACL、RPC、
ucitrack 和 init 的实际字节，并拒绝旧入口残留。新版安装及迁移测试与实际新固件/设备验收分开记录。

## 构建与下载

1. 进入 Actions，选择 `TR3000`。
2. 默认使用 `SOURCE_MODE=latest` 和 `PLUGIN_MODE=latest`，跟随 `VIKINGYFY/immortalwrt@owrt`
   及插件分支的最新提交。需要复现版本锁时，可分别将两个模式切换为 `locked`。
3. 先用 `TEST=true` 检查配置，再用 `BUILD_ONLY=true` 完整编译并校验固件。
4. 需要发布时关闭 TEST 和 BUILD_ONLY。编译通过后，独立发布 job 下载本次 Artifact，
   复核校验和，再上传 draft Release 并公开；不再事后下载或裁剪“最新 Release”。

校验要求来自 `Profiles/TR3000-512.json`，包括必需软件包、tar 结构和设备元数据，
并检查实际 FIT 中的 DTB 分区，以及 squashfs 内的关键脚本、启动链接和构建标签。
附件包含 sysupgrade、实际配置、manifest、校验和与版本及校验证据。
标签包含机型、源码、分支、时间、run ID 和 attempt；非 main 分支额外使用 `preview-` 前缀。

`Auto-Clean.yml` 按型号和正式 / 测试渠道分别保留最近 3 个已发布 Release，每天香港时间 05:21 执行。

## 升级与验证

### 一键 OTA

新构建在“系统 → 固件升级”提供 TR3000 512MB 页面。检查更新后点击“升级（保留配置）”，
确认后自动下载、校验并调用系统 `sysupgrade`，也可选择不保留配置。只识别本仓库的
`TR3000-512-VIKINGYFY-owrt-` 正式渠道，排除草稿、测试渠道、其他机型及没有 512MB
兼容描述的旧 Release。元数据来自 GitHub API，镜像站只负责文件传输。

本机检查板型、内核 MTD 分区、运行设备树中的 UBI 起点/长度、NAND 页和擦除块，以及实际
UBI 根文件系统。发布端仅在实际 FIT/DTB/squashfs 验证通过后生成 `tr3000-ota-image.json`；
下载时再将其中的机型、512MB 布局、标签、文件名、大小和摘要与 Release 核对。
升级前重验本机布局、已下载文件及 `sysupgrade -T`；不使用强制刷写、裸写 MTD 或修改 U-Boot。

默认下载目录 `/tmp/tr3000-ota` 位于内存，重启后清空；可将 `tr3000_ota.main.dir` 指向
已挂载的外部存储。指定版本回退必须使用已下载且带完整校验记录的镜像，离线时也重新核对。
这里的回退是重新刷入指定版本，并非 A/B 自动恢复。升级前的临时备份应另行保存；
保留配置升级会在重启后核对构建标签，不保留配置时旧任务记录也会清空。

```sh
tr3000-ota check
tr3000-ota upgrade --keep --yes
tr3000-ota upgrade --wipe --yes
tr3000-ota upgrade --tag TR3000-512-VIKINGYFY-owrt-实际版本 --keep --yes
```

每日检查仅提示可用版本，不自动刷机。`enabled=0` 关闭页面操作及定时检查，
`auto_check=0` 单独关闭定时检查。下载、升级和 CLI 自更新共用文件锁；CLI 自更新只从
兼容正式 Release 取脚本，要求运行 ABI 及固件内分区检查库摘要一致，保留旧脚本备份。
首次接入需要手动刷入含该功能的新固件；代码提交不会给当前设备或旧 Release 自动增加页面。

### 手动升级

使用名称包含 `cudy_tr3000-v1-squashfs-sysupgrade`、后缀为 `.bin` 的镜像。
升级前备份配置、核对 sha256，执行 `sysupgrade -T /tmp/实际固件文件名.bin`，通过后再升级。
首次跨源码升级建议不保留配置。

默认 LAN 地址在构建期设置；已删除强制重设 LAN、主题和加速选项的自定义首启脚本。
保留配置升级时，这些旧脚本不再覆盖用户选择；F50 的自动接入行为见下方注意点。

## 已知注意点

1. **分区补丁是硬门槛**：`patch-layout.sh` 若因上游 DTS 变动而断言失败，构建会直接中止，
   这是故意的——镜像大小/UBI 布局不对的固件刷进 512MB 机器会变砖。
2. **保留配置升级**：旧 `network.F50` 会迁移为 `f50` 并保留设置；已有 `f50` 的协议、DNS、metric、停用开关和防火墙区域保留，设备绑定按 USB 枚举结果更新。
3. **固件体积**：基础与功能片段保留 Samba、Btrfs、NVMe、OpenVPN 等选择。
   上游包名消失会记录到 `config-resolution.json`；必需包丢失会阻止构建通过。

## 真机联调记录（2026-10-25，设备 192.168.6.1）

F50（ZTE，USB 共享）从「完全没网」到「全链路通」踩过的坑，都是真实量到的：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | F50 自己有网，TR3000 发的 WiFi 一点网都没有 | `/sys/bus/usb/devices` 只有 `usb1`/`usb2` 两个根 Hub —— 那根 USB 线是**纯充电线**（无 D+/D-），压根没枚举出设备 | 换一根确认能传数据的线 |
| 2 | 换线后 USB 枚举、拿到 IP，但 `ping 223.5.5.5` 100% 丢包，看着像没网 | **这条链路上 ICMP 被屏蔽**。同时 `curl http://223.5.5.5/` 返回 404（0.07s），TCP 一直是通的 | 别用 ping 判断生死，用 `curl`/TCP 复测 |
| 3 | **「没有下载速度」**：偶尔网页能打开，镜像站却直接 `Could not resolve host` | F50 自带的 DNS `192.168.0.1` 对 CNAME 链（`mirrors.aliyun.com` → `w.alikunlun.com`）只回 CNAME、不回 A 记录，客户端拿不到 IP；直连 114 查同一域名 10/10 成功 | 固件改成 `peerdns=0` + 三个公共 DNS，实测解析 10/10、下载 5.2 MB/s |
| 4 | 早期 `network.F50.device='eth2'` 报「网络设备不存在」 | 设备名写死，换线/重新枚举后名字一变就废 | `tr3000-usbwan.sh` 按 USB 总线实时探测 |

验证通过的实测值：

```
eth2: 192.168.0.171/24, default via 192.168.0.1
ping 192.168.0.1        → 0.6 ms
curl http://223.5.5.5/  → HTTP 404, 0.07 s      # TCP 出网
curl --interface 192.168.6.1 http://223.5.5.5/ → 404, 2.5 s   # LAN→NAT 验证
客户端出口 IP            → 183.194.125.118（中国移动·上海，F50 的 5G 出口）
DNS 解析 10/10           → 114 / 223.5.5.5 / 119.29.29.29
镜像站下载 38.5 MB       → 7.3 s，5.25 MB/s（约 42 Mbps）
```

> 排查提示：客户端「上不了网」先分清是**解析失败**还是**转发失败**。
> 路由器上 `curl --interface 192.168.6.1 http://223.5.5.5/` 能 404，就说明 NAT 与转发没问题，问题只剩 DNS。
